# Nexio Import, Export and Data Portability Specification

Version: 1.0  
Status: Official  
Authority Level: Financial Import, Export, File Processing and Data Portability Standard  
Applies To: Web, Desktop, Tablet, Mobile Web, Android, Accounts, Transactions, Transfers, Categories, Goals, Reports, Attachments, CSV, JSON, Spreadsheet Files, Backup Packages, Provider Imports, User Data Exports, Privacy Requests, Account Deletion, Support and External Storage

---

# Purpose

This document defines the official Import, Export and Data Portability architecture for Nexio.

It establishes how Nexio should:

- Receive financial files
- Select files safely
- Validate file metadata
- Parse supported formats
- Interpret financial Amounts
- Interpret Currency
- Interpret Dates
- Map Accounts
- Map Categories
- Detect possible duplicates
- Represent ambiguous rows
- Preview Import candidates
- Confirm financial records
- Handle partial failure
- Resume interrupted processing
- Export financial data
- Generate privacy-related data packages
- Protect exported files
- Deliver files through approved channels
- Support Android file handling
- Support Web file handling
- Prevent spreadsheet formula injection
- Prevent path, archive and content attacks
- Preserve owner isolation
- Preserve exact financial meaning
- Preserve provenance
- Support user-controlled portability
- Support Account deletion
- Support audit and reconciliation
- Use AI only for bounded assistance

The objective is to ensure that Import and Export never become:

```text
A hidden financial-data writer

An automatic duplicate creator

An implicit Currency converter

A formula-execution path

A cross-owner data bridge

A file-upload vulnerability

A replacement for canonical validation

An unprotected financial-data leak

An irreversible bulk operation without review

A provider lock-in mechanism
```

# Import and Export Constitutional Principles

## Imported Data Is Untrusted

Every imported file, row, cell, field, archive entry, formula, link, filename and metadata value must be treated as untrusted input.

The source may be:

- User-created
- Generated by another application
- Corrupted
- Outdated
- Malicious
- Incomplete
- Mislocalized
- Duplicated

---

## Import Must Not Bypass Canonical Commands

Confirmed imported records must use the same:

```text
Account commands

Transaction commands

Transfer commands

Goal commands

Validation

Authorization

Idempotency

Operation identity

Persistence

Synchronization
```

used by records created manually.

---

## Parsed Rows Are Candidates, Not Financial Records

Parsing a file may create:

```text
Import candidates
```

It must not automatically create canonical financial entities unless an explicitly approved bounded mode exists.

Default model:

```text
File

↓

Parsed rows

↓

Normalized candidates

↓

Validation

↓

Duplicate review

↓

User confirmation

↓

Canonical commands
```

---

## Import Must Preserve Source Meaning

Nexio must not silently reinterpret:

- Income as Expense
- Expense as Income
- Transfer as unrelated entries
- Decimal separator
- Date order
- Currency
- Account ownership
- Sign convention

---

## Import Must Not Guess Material Financial Meaning Silently

When Nexio cannot determine:

- Currency
- Date
- Amount sign
- Transaction type
- Account
- Transfer relationship

the row must become:

```text
needs_review
```

or:

```text
rejected
```

It must not receive an unsupported automatic guess.

---

## Currency Must Be Explicit

Every imported financial candidate must resolve to a known Currency before canonical confirmation.

Examples:

```text
BRL

USD

EUR
```

A symbol alone may be ambiguous.

---

## Import Must Not Perform Implicit Currency Conversion

Nexio must not convert:

```text
R$ 84,90

to

US$ 16.00
```

or any other Currency without a separately approved conversion capability, explicit rate, explicit date, explicit source and user confirmation.

---

## Money Must Remain Exact

Imported Money should be normalized into the canonical exact representation.

Do not persist financial Amounts using binary floating-point approximations.

---

## Locale Parsing Must Be Explicit

For `pt-BR`, the following may represent valid BRL display values:

```text
R$ 84,90

R$ 1.250,00

1250,00
```

The parser must not automatically assume that:

```text
1.250
```

means the same thing in every source locale.

It could represent:

```text
One thousand two hundred and fifty
```

or:

```text
One point two five zero
```

depending on the source convention.

---

## Dates Must Preserve Calendar Meaning

A value such as:

```text
03/04/2026
```

is ambiguous without a source locale or explicit date format.

It may mean:

```text
3 April 2026
```

or:

```text
4 March 2026
```

Ambiguous Dates require review.

---

## Transfers Must Remain One Logical Operation

Nexio should detect possible Transfer pairs, but it must not silently merge unrelated records.

A confirmed Transfer must preserve:

```text
One logical Transfer identity

Source Account effect

Destination Account effect

Currency compatibility

Atomicity

Idempotency
```

---

## Import Must Be Idempotent

Reprocessing the same file or confirming the same candidate set must not create uncontrolled duplicates.

---

## Duplicate Detection Is Advisory until Proven

A possible duplicate is not automatically a duplicate.

Detection may compare:

```text
Owner

Account

Amount

Currency

Date

Type

Description

Source identifier

Provider identifier

Import batch

Transfer relationship
```

The final decision may require user or deterministic provider evidence.

---

## Import Provenance Must Be Preserved

Every confirmed imported record should be traceable to:

```text
Import batch

Source type

Original row reference

Parser version

Mapping version

Confirmation time

Owner

Canonical operation
```

---

## Original Files Must Not Become Financial Authority

The source file may be retained temporarily for processing or audit according to policy.

Canonical Product state must derive from confirmed entities, not from rereading the file on every Product load.

---

## Export Must Use Canonical Product State

Exports should read from authoritative repositories and deterministic reporting services.

They must not reconstruct financial truth from:

- Notification history
- Analytics events
- Cached UI strings
- Stale browser state
- Search index
- Help content
- Assistant history

---

## Export Scope Must Be Explicit

Every Export should define:

```text
Owner

Entity types

Accounts

Currencies

Date range

Status inclusion

Deleted or archived behavior

Attachments

Format

Locale

Time zone
```

---

## Export Must Not Combine Currencies Incorrectly

An Export may list multiple Currencies.

It must not calculate a combined total unless an approved conversion model exists.

Example:

```text
BRL total:
R$ 2.085,25

USD total:
US$ 120.00
```

These remain separate.

---

## Export Must Preserve Machine Meaning

A human-readable value may appear as:

```text
R$ 1.250,00
```

A machine-readable field should also include explicit structured meaning, such as:

```json
{
  "currency": "BRL",
  "minorUnits": 125000
}
```

or the canonical approved equivalent.

---

## Exported Files Are Sensitive

Exported files may contain:

- Accounts
- Transactions
- Financial Amounts
- Dates
- Notes
- Categories
- Goals
- Personal identifiers
- Attachments

They require clear handling guidance and controlled delivery.

---

## Export Delivery Does Not Prove User Receipt

An Export may be:

```text
generated

available

downloaded

sent_to_provider

provider_accepted

delivered

expired
```

These states are distinct.

---

## File Download Must Require Current Authorization

Protected Exports should require:

```text
Authentication

Current owner

Export ownership

Expiration validation

Current access policy
```

---

## Public Export Links Are Prohibited by Default

A financial Export should not be exposed through a predictable or indefinitely valid public URL.

---

## Import and Export Must Be Accessible

Every workflow must support:

- Keyboard
- Screen reader
- Large text
- Mobile reflow
- Android file picker
- Progress announcements
- Error summaries
- Candidate-table alternatives
- Review without color-only meaning

---

## File Processing Must Be Resumable Where Practical

Large or long-running processing should support:

- Progress state
- Restart
- Cancellation
- Safe Retry
- Batch identity
- Partial results
- Recovery

---

## Cancellation Must Be Explicit

Cancelling parsing should not create canonical records.

Cancelling confirmation should preserve already committed records and accurately show the partial result.

---

## Partial Success Must Remain Visible

A batch may contain:

```text
Confirmed candidates

Rejected candidates

Candidates requiring review

Skipped duplicates

Failed commands
```

Do not report the entire Import as successful when some records failed.

---

## Export Failure Must Not Corrupt Product State

An Export is a read operation except for its own job and audit records.

Failure must not change:

- Accounts
- Transactions
- Transfers
- Goals
- Balances
- Reports

---

## Import and Export Must Respect Account Deletion

Account deletion must address:

- Uploaded source files
- Parsed candidates
- Import batches
- Export jobs
- Generated files
- Provider copies
- Delivery links
- Audit records
- Required retention

---

## File Providers Must Remain Replaceable

Cloud storage, document picker, email delivery and Import-provider logic must remain behind Adapters.

---

## AI Must Not Become the Import Authority

AI may assist with:

- Suggested column mapping
- Description categorization
- Candidate explanation
- Error summarization

AI must not independently:

- Confirm records
- Convert Currency
- Guess ambiguous Dates as fact
- Merge Transfers
- Resolve ownership
- Override duplicate controls
- Mark Export complete

# Formula Cell Handling

```text

or

Require user review
```

Nexio must never evaluate imported spreadsheet formulas.

---

# Macro Handling

Macro-enabled files should be:


# Sign Rule Examples

## Separate Type

```text
type:
Expense

amount:
84,90
```

Expected canonical meaning:

```text
Expense of R$ 84,90
```

---

## Signed Amount

```text
amount:
-84,90
```

may mean Expense only when the source schema explicitly defines negative as outflow.

---

## Debit and Credit Columns

Example:

```text

84,90

credit:
empty
```

may indicate Expense under an approved provider schema.

---

# Sign Ambiguity

The parser must not combine multiple sign conventions without warning.

Example:

```text
type:
Expense

amount:
-84,90
```

The schema must define whether the negative sign is expected, redundant or invalid.

# Part 1 Anti-Patterns

The following are prohibited:

## Parsing Equals Importing

Creating canonical records immediately after reading a file.

## File Extension Trust

Accepting a file based only on `.csv`, `.json` or `.xlsx`.

## Float Money Parsing

Using binary floating point as canonical financial representation.

## Silent Locale Guess

Interpreting `1.250` without source-locale confidence or review.

## Symbol-Only Currency

Treating `$` as a complete Currency identity.

## Silent Currency Conversion

Converting between BRL and another Currency without explicit authority.

## Date Guessing

Automatically interpreting `03/04/2026` without a declared format.

## Transfer Auto-Merge by Amount

Combining two records only because their Amounts match.

## Duplicate Auto-Deletion

Removing a candidate or existing record without evidence and review.

## Tutorial-Only Import Writer

Using a special Import writer that bypasses canonical commands.

## Whole-Batch False Success

Reporting success while candidate commands failed.

## New Identity on Retry

Creating a new candidate or command identity after timeout.

## Macro Execution

Allowing spreadsheet macros to execute.

## Formula Evaluation

Evaluating imported formulas.

## Spreadsheet Formula Injection

Exporting user text that executes when opened.

## Archive Bomb Exposure

Expanding archives without limits.

## External Link Fetching

Resolving remote spreadsheet or document links during parsing.

## Raw Internal File Path on Android

Sharing an internal filesystem path instead of a protected content URI.

## Public Permanent Export URL

Making sensitive financial files indefinitely public.

## Export Delivery Equals Receipt

Treating provider acceptance as user access.

## Export as Backup without Recovery Contract

Calling a CSV Export a full backup when it cannot restore complete Product state.

## Support File Collection through Informal Channel

Requesting a full financial file through unapproved email or chat.

## AI Auto-Confirmation

Allowing AI to decide and create imported financial records.

## Prompt Injection Authority

Allowing imported text to change Import or Assistant rules.

## Account Deletion without File Cleanup

Leaving source files, candidates, Exports or provider copies active after deletion.

Every Nexio file, row, candidate, mapping, duplicate decision, confirmation command, Export job, generated file, download link and portability package must answer:

- Rejects the file.
- Keeps the row as an unconfirmed candidate.
- Requires explicit Currency.
- Requires explicit Date format.
- Requires user mapping.
- Marks a possible duplicate.
- Avoids Transfer merging.
- Avoids automatic confirmation.
- Avoids Currency conversion.
- Preserves the original batch identity.
- Uses generic safe text rendering.
- Revokes the Export link.
- Deletes temporary files.
- Escalates for technical review.
- Blocks the release.

Import is not successful because a file was parsed.

Export is not successful because a file was generated.

Import is successful only when approved candidates become correct owner-scoped canonical records without duplication or lost meaning.

Export is successful only when the authorized owner receives a complete, explicit, secure and portable representation of the selected canonical data.

# Part 2 Anti-Patterns

The following are prohibited:

## New Batch on Every Retry

Losing stable Import identity during upload or parser failure.

## Parsing before Owner Validation

Reading or uploading financial files before current-owner authorization.

## One Generic Progress Percentage

Combining upload, parsing, validation and confirmation into misleading progress.

## Silent Format Mismatch

Processing XLSX content as CSV because of the filename.

## Parser with Open Network Access

Allowing imported content to trigger remote retrieval.

## Automatic Mapping without Visibility

Hiding Amount, Currency, Date or Account mapping from the user.

## Saved Mapping without Version

Reusing incompatible assumptions after source changes.

## Global Currency Override

Overwriting explicit row Currencies with a batch default.

## Amount Normalization without Raw Value

Removing the ability to compare source and proposed financial meaning.

## Name-Only Account Authority

Mapping Accounts solely because names match.

## Similarity Equals Duplicate

Skipping legitimate records because Amount and Date are similar.

## Similarity Equals Transfer

Merging unrelated Income and Expense candidates automatically.

## Hidden Rows Selected Automatically

Including filtered unresolved candidates in bulk confirmation.

## Confirmation without Snapshot

Allowing the reviewed candidate set to change during final confirmation.

## Batch Success from Majority

Calling an Import successful because most records committed.

## Retry with New Canonical Operation

Creating duplicates after confirmation timeout.

## Refresh Creates New Import

Starting another batch after browser refresh or Android process death.

## Cached Formula Value as Fact

Treating an unexecuted workbook formula result as canonical truth.

## External Workbook Fetch

Loading remote spreadsheet content during parsing.

## Provider Adapter as Writer

Allowing provider mapping code to create financial entities directly.

## Download Link as Authorization

Treating possession of an Export URL as owner authority.

## Android Raw Path Sharing

Exposing internal storage paths.

## Provider Acceptance as Delivery

Claiming an Export reached the user because a provider accepted it.

## Partial Export without Manifest

Generating incomplete files without disclosing missing data.

## Export Retry with Changed Scope

Reusing one job identity for a materially different Export.

## Account Deletion while Jobs Remain Active

Allowing parsers, confirmations or delivery jobs to continue ordinary processing after deletion restriction.

# Part 2 Import and Export Constitutional Rule

Every file-selection result, upload operation, parser job, schema decision, mapping, normalized candidate, duplicate match, Transfer pair, confirmation snapshot, canonical command, Export worker, generated artifact, protected link and external delivery must answer:

```text
Does this operation preserve the same owner, source, schema, locale, exact Amount, explicit Currency, candidate identity and canonical operation identity from initial file access through final confirmation or protected delivery, including interruption, Retry, Account switching, provider timeout and Account deletion?
```

When the answer is uncertain, prefer the action that:

- Keeps the source unprocessed.
- Rejects the file.
- Preserves the existing batch.
- Requires explicit mapping.
- Preserves the original raw value.
- Requires explicit BRL or other Currency identity.
- Marks the candidate for review.
- Marks a possible duplicate.
- Keeps possible Transfers separate.
- Prevents confirmation.
- Reconciles the original operation.
- Reports partial success.
- Revokes the download.
- Deletes temporary files.
- Disables the provider.
- Blocks the release.

A completed parser job does not mean financial records were imported.

A generated file does not mean the owner received a complete or secure Export.

Import is complete only when the reviewed candidates are confirmed through canonical owner-scoped commands and every result is reconciled.

Export is complete only when the approved scope is represented accurately, the artifact passes integrity and content-safety checks, and current authorization protects every access and delivery path.

```text
Pause new optional work.

Preserve existing canonical records.

Keep batches and jobs in classified states.

Use alternate provider only when approved.

Avoid claiming completion.

Communicate only when useful.
```

# Support Training Module — Parsing versus Import

Agents should explain:

```text
A parsed file creates reviewable candidates.

```

# Support Training Module — Money and Currency

Agents should recognize:

```text
R$ 84,90

R$ 1.250,00

BRL
```

and understand that:

- `R$` is a display symbol.
- `BRL` is the explicit Currency identity.
- `1.250` may be ambiguous without source rules.
- Nexio does not convert Currency automatically.

---

# Support Training Module — Date Ambiguity

Agents should recognize that:

```text
03/04/2026
```

may require confirmation of:

```text
DD/MM/YYYY

or

MM/DD/YYYY
```

---

# Support Training Module — Duplicate Review

Agents must not tell users:

```text
Delete every matching record.
```

They should identify whether the match is:

```text
exact source duplicate

or

possible similarity duplicate
```

---

# Support Training Module — Transfer Review

Agents should understand:

```text
One Transfer has two Account effects.

It should not become unrelated Income and Expense.

Different Currencies require an approved model.
```

---

# Support Training Module — Unknown Confirmation Outcome

Agents should:

- Preserve the original candidate and operation identity.
- Avoid telling the user to confirm again immediately.
- Check reconciliation status.
- Escalate when the aging threshold is exceeded.

# Support Scenario — Ambiguous BRL Amount

Prompt:

```text
A CSV row contains “1.250” and the user says it should be Brazilian reais.
```

Expected Support guidance:

```text
Do not assume whether the value means R$ 1.250,00 or R$ 1,25.

Confirm the source format and decimal convention before Import.
```

---

# Support Scenario — Duplicate Import

Prompt:

```text
The user imported the same file twice and sees possible duplicate warnings.
```

Expected:

```text
Review Import provenance and exact source identifiers.

Do not delete records solely because Amount and Date match.

Use the duplicate comparison and batch history.
```

---

# Support Scenario — Export Link Expired

Expected:

```text
The expired link cannot be reactivated directly.

Confirm the current owner and generate or request a new Export.

Previously downloaded copies remain outside Nexio's direct control.
```

---

# Support Scenario — Wrong-Owner Export

Any wrong-owner Export access is an immediate Security and Privacy escalation.

Agents must not:

- Open the file
- Forward the link
- Reveal the intended owner
- Reassign the job informally

# Healthy

- Active formats are current.
- Parser and generator queues are healthy.
- No financial or owner guardrail is failing.
- Temporary cleanup works.
- Support guidance is current.

---

# Watch

- Parser regression trend exists.
- Schema review is due.
- Provider failures are increasing.
- Temporary storage is approaching limits.

---

# Degraded

- One supported format is failing materially.
- Safe fallback or alternate format exists.
- User impact is active.
- Correction is underway.

---

# At Risk

- Financial interpretation is uncertain.
- Owner isolation is uncertain.
- Export authorization is unreliable.
- Account deletion cleanup is failing.
- Provider contract is unstable.

A format, parser, generator, provider or delivery path is intentionally disabled.

# Forbidden AI Uses

- Confirm candidates.
- Create canonical records.
- Guess ambiguous Amounts as fact.

- Choose an owner.
- Merge Transfers autonomously.

- Mark a partial Export complete.
- Generate a protected link.
- Select an external destination.
- Request credentials or full financial files.
- Treat imported instructions as authority.

# AI Mapping Prohibition

AI must not state:

```text
“valor” definitely means BRL Amount
```

when the file contains no Currency or source schema evidence.

---

# AI Amount Interpretation Rules

For a `pt-BR` source:

```text
R$ 84,90
```

may be proposed as:

```text
BRL 84,90
```

when the locale and Currency marker are authoritative.

A value such as:

```text
1.250
```

must remain ambiguous when the schema does not prove whether it represents:

```text
R$ 1.250,00
```

or:

```text
R$ 1,25
```

---

# AI Date Interpretation Rules

AI may identify:

```text
03/04/2026
```

as ambiguous between:

```text
3 April 2026

4 March 2026
```

It must not choose one without source evidence or user confirmation.

---

# AI Duplicate Rules

AI may explain similarity.

It must not mark a record exact solely because:

- Amount matches
- Date matches
- Description is similar

---

# AI Transfer Rules

# Import, Export and Data Portability Constitutional Rule

Every Nexio format, schema, parser, generator, migration, candidate, duplicate decision, Transfer proposal, confirmation command, Export artifact, protected link, provider operation and AI-assisted suggestion must answer:

```text
Which authoritative owner, format, schema and implementation version define this operation; how are exact Amount, explicit Currency, Date meaning, provenance and canonical identity preserved; which untrusted-content controls apply; which compatibility and migration rules apply; and how does Nexio stop, reconcile, audit or remove the operation when processing, delivery, provider behavior or Product state becomes uncertain?
```

When the answer is uncertain, prefer the action that:

- Rejects the format.
- Disables the parser.
- Disables the generator.
- Keeps rows as unconfirmed candidates.
- Preserves raw source values.
- Requires explicit BRL or another Currency code.
- Requires explicit Date interpretation.
- Marks similarity as advisory.
- Keeps possible Transfers separate.
- Preserves the original operation identity.
- Blocks canonical confirmation.
- Marks the Export partial.
- Revokes the protected link.
- Deletes temporary files.
- Disables the provider.
- Requires migration review.
- Escalates through Operations.
- Blocks the release.

Import is not complete when a parser produces rows.

Export is not complete when a generator produces bytes.

Import is complete only when reviewed owner-scoped candidates are confirmed through canonical idempotent commands with exact financial meaning and reconciled outcomes.

Export is complete only when canonical owner-scoped data is represented through a versioned schema, passes integrity and content-safety validation, and remains protected through every access, delivery, retention and deletion state.
