# Nexio Synchronization, Offline Operation, Conflict Resolution and Data Consistency Specification

Version: 1.0  
Status: Official  
Authority Level: Platform Synchronization, Client Replica, Offline Operation and Distributed Data Consistency Standard  
Applies To: Android Application, Web Application, Backend Services, APIs, Database, Local Storage, IndexedDB, Mobile Databases, Caches, Background Jobs, Financial Resources, Transactions, Accounts, Budgets, Goals, Recurring Transactions, Reports, Notifications, Preferences, Imports, Exports, Authentication Sessions, Device Registration, Audit, Security, Privacy, Accessibility, Operations and Support

---

# Purpose

This specification defines the official Synchronization, Offline Operation, Conflict Resolution and Data Consistency architecture for Nexio.

It establishes how Nexio must:

- Synchronize canonical backend Resources with Android and Web clients.
- Distinguish authoritative server state from local replicas.
- Support safe offline access.
- Support approved offline mutations.
- Preserve stable Resource identity.
- Preserve Owner and Account isolation.
- Prevent duplicate financial mutations.
- Detect stale Resource versions.
- Detect synchronization gaps.
- Resolve or surface concurrent changes.
- Preserve pending local operations across Application restarts.
- Recover safely after network interruption.
- Handle retries idempotently.
- Handle partial synchronization.
- Handle deleted and archived Resources.
- Handle Owner switching on shared Devices.
- Prevent previous Owner data from appearing after sign-out.
- Define local-data retention.
- Define synchronization cursors and sequence boundaries.
- Define bootstrap and full-refresh behavior.
- Define incremental synchronization.
- Define local optimistic state.
- Define rollback and compensation behavior.
- Define background synchronization.
- Define synchronization freshness and health.
- Support consistent behavior across Android and Web.
- Preserve financial-integrity requirements.
- Preserve Security and Privacy requirements.
- Support synchronization investigation and Audit reconstruction.
- Prevent client replicas, caches or offline state from becoming independent sources of truth.

This document applies to every Nexio component that stores, reads, mutates, queues, uploads, downloads, merges, invalidates, replays, retries, caches or reconciles data outside the canonical backend persistence boundary.

# Constitutional Principle

The canonical Nexio backend is authoritative for persisted shared Product and financial state.

Android, Web, local databases, IndexedDB, Service Workers, browser caches, in-memory stores and offline queues are subordinate replicas or provisional intent stores.

Every synchronized Resource must answer:

```text
Which canonical Owner does the Resource belong to?

Which Account or Resource scope applies?

Which stable Resource identifier is used?

Which Resource version is current?

Which server sequence or data boundary produced the replica?

Which client or Device created the local operation?

Was the local state accepted by the backend?

Was the operation rejected, duplicated or conflicted?

Which synchronization cursor was used?

Is the local representation current, stale, pending, conflicted or unavailable?

Can the synchronized state and every mutation be reconstructed?
```

A client-visible value must not be treated as canonical merely because:

- It exists in local storage.
- It was previously downloaded.
- It appears in a Dashboard.
- It was optimistically rendered.
- It survived an Application restart.
- It was created while offline.
- It appears newer according to the Device clock.
- It was accepted by a local validation function.
- It was generated by a Service Worker.
- It was restored from a client backup.

# Canonical Authority

The backend is authoritative for:

- Canonical Resource existence.
- Owner assignment.
- Account assignment.
- Persisted monetary values.
- Persisted Transaction states.
- Resource versions.
- Financial sequence.
- Server timestamps.
- Authorization.
- Reconciliation state.
- Audit state.
- Final mutation outcome.
- Cross-Device synchronization state.

Clients may preserve replicas and provisional intents.

They must not silently override canonical state.

---

# Deterministic Identity

Every synchronized Resource must have a stable identifier.

The same logical Resource must not receive unrelated identifiers on:

- Android.
- Web.
- Backend.
- Offline queue.
- Local database.
- Export.
- Notification.
- Audit Event.

---

# Owner Isolation

Every synchronization request, cursor, local partition, cache key, offline queue and conflict record must preserve Owner scope.

A synchronization process must never:

- Download another Owner's Resource.
- Upload an intent using another Owner's Account.
- Reuse another Owner's cursor.
- Reuse another Owner's cache partition.
- Apply another Owner's local operation.
- Display another Owner's pending mutation.
- Preserve another Owner's private data after Account switching.

Cross-Owner synchronization is a Critical Security, Privacy and financial-integrity failure.

---

# Account Isolation

Account-scoped Resources must preserve Account ownership.

The backend must verify that every Account identifier included in:

- Sync requests.
- Mutation intents.
- Filters.
- Conflict resolution.
- Local Resource relationships.
- Financial operations.

belongs to the canonical authenticated Owner.

---


# Idempotent Mutation

The same logical mutation must not be applied more than once because of:

- Network Retry.
- Background Job Retry.
- Application restart.
- Queue redelivery.
- Service Worker replay.
- Device reconnection.
- Manual Retry.
- Timeout with unknown outcome.
- Multiple tabs.
- Multiple Android workers.

---

# Ordered Change Processing

Where order affects meaning, synchronized changes must use a defined ordering mechanism.

Potential mechanisms include:

- Resource version.
- Owner synchronization sequence.
- Account financial sequence.
- Server Event sequence.
- Immutable change identifier.
- Database commit order.

Device timestamps must not be the sole authority for ordering shared Resources.

---

# Gap Detection

Clients and backend synchronization services must detect missing sequence ranges where sequencing is used.

A sequence gap must not be ignored silently.

---

# Offline Safety

Offline capability must preserve:

- Owner scope.
- Resource scope.
- Exact financial values.
- Operation identity.
- Validation state.
- Pending state.
- Conflict state.
- Retry state.
- Expiration.
- Local protection.

Offline capability must not create a false impression that a provisional operation is already authoritative.

---

# Conflict Transparency

When a conflict cannot be resolved deterministically through an approved policy, Nexio must preserve and present the conflict.

The system must not silently choose the most convenient value.

---

# Deletion Integrity

A deleted or archived Resource must not reappear because a stale client uploads an obsolete copy.

Deletion, archive and restoration semantics must be explicit.

---

# Freshness Visibility

Clients should distinguish:

```text
Stale

Offline

Synchronization failed

Conflict requires review
```

# Core Synchronization Principles

The Nexio Synchronization architecture is governed by:

```text
Server Authority

Stable Resource Identity

Explicit Resource Version

Explicit Synchronization Boundary

Owner-Partitioned Replicas

Idempotent Operations

Append-Safe Change Tracking

Conflict Detection Before Overwrite

Deletion Tombstones

Schema Compatibility

Freshness Transparency

Local Data Minimization

Safe Recovery
```

---

# Server Authority Principle

The server determines whether an offline or online mutation becomes canonical.

A local mutation may be:

```text
Pending

Accepted

Rejected

Conflicted

Duplicated

Expired

Cancelled
```

---

# Stable Resource Identity Principle

A Resource created offline should receive a stable client-generated provisional identifier or client creation key.

The server may preserve that identifier or map it to a canonical identifier.

The mapping must remain stable.

---

# Explicit Resource Version Principle

Every mutable Resource should have:

```text
resourceVersion
```

A successful canonical mutation increments or replaces the version according to the Resource policy.

---

# Explicit Synchronization Boundary Principle

Every synchronization operation should identify the data boundary used.

Potential boundaries include:

- `asOf` server time.
- Owner synchronization sequence.
- Resource change sequence.
- Cursor.
- Snapshot version.
- Dataset version.

---

# Owner-Partitioned Replica Principle

Local data should be partitioned by canonical Owner.

Recommended conceptual key:

```text
environment

+

applicationId

+

ownerId

+

resourceType

+

resourceId
```

---

# Idempotent Operation Principle

Every mutation capable of Retry should have:

```text
operationId

idempotencyKey

requestHash

resourceId

ownerId
```

---

# Append-Safe Change Tracking Principle

Change tracking should avoid losing intermediate Events when multiple mutations occur between client synchronization requests.

---

# Conflict Detection Before Overwrite Principle

The server must validate the expected Resource version before accepting an update where concurrent mutation matters.

---

# Deletion Tombstone Principle

Deletion must produce a synchronization representation sufficient to prevent stale resurrection.

---

# Schema Compatibility Principle

The client and backend must negotiate or validate compatible schema versions.

---

# Freshness Transparency Principle

The client should preserve:

```text
lastSuccessfulSyncAt

lastAttemptedSyncAt

currentCursor

syncState

pendingMutationCount

conflictCount
```

---

# Local Data Minimization Principle

Clients should store only the data required for approved offline and Product behavior.

---

# Safe Recovery Principle

When local state cannot be trusted, Nexio should prefer:

- Preserving unsent mutation intents.
- Clearing rebuildable replicas.
- Performing a full authenticated refresh.
- Reapplying only validated pending intents.
- Avoiding silent financial loss.

---

# Resource Version

A Resource version should be:

- Monotonic within one Resource.
- Changed only by canonical accepted mutation.
- Returned in every mutable Resource response.
- Required for conditional update where conflict risk exists.


The version contract must remain consistent per Resource Type.

# Cursor Properties

A cursor must be:

- Owner-bound.
- Environment-bound.
- Application-bound where required.
- Integrity-protected.
- Opaque to clients where practical.
- Expiring.
- Scope-aware.
- Version-aware.

---

# Cursor Scope

A cursor may apply to:

```text

One Resource Type

One Account

One bounded dataset

One Notification stream
```

---

# Cursor Integrity

The backend must reject a cursor that was:

- Modified.
- Reused for another Owner.
- Reused in another environment.
- Reused for an incompatible filter.
- Expired beyond supported recovery.
- Issued for an unsupported schema version.

---

# Cursor Expiration

On cursor expiration, the server may require:

- Cursor renewal.
- Bounded delta recovery.
- Full Resource Type refresh.
- Full Owner replica bootstrap.

The behavior must avoid losing pending local mutations.

---

# Cursor and Authorization

A valid cursor does not grant access.

Authentication and Authorization must be evaluated independently.

The backend deleted the Resource while a local replica still existed.

---

# Invalidated State

The Resource must not be used until refreshed or removed.

# Foundational Synchronization Rule

A local Resource is not authoritative merely because it is visible.

An offline mutation is not complete merely because it was stored on the Device.

A synchronization attempt is not successful merely because a network request returned.

A conflict is not resolved merely because one value was displayed.

A deletion is not safe merely because a local row was removed.

Synchronization is trustworthy only when Nexio can establish:

```text
The canonical Owner

The Account and Resource scope

The stable Resource identity

The canonical Resource version

The synchronization sequence or data boundary

The client and Device identity

The local mutation intent

The stable operation identity

The expected base version

The backend validation decision

The accepted canonical result or controlled rejection

The conflict or duplicate outcome

The final client acknowledgement

The cursor and freshness state

The Evidence required to reconstruct the lifecycle
```

When Resource identity, Owner scope, Account scope, version, cursor integrity, local integrity, mutation intent, Authorization, financial meaning or conflict resolution cannot be established, Nexio must prefer the action that:

- Stops the affected synchronization.
- Preserves pending unsent Intents safely.
- Prevents cross-Owner upload or display.
- Rejects stale overwrite.
- Preserves canonical server state.
- Marks the local state stale or conflicted.
- Uses a full authenticated refresh.
- Prevents duplicate Retry.
- Applies Tombstones.
- Blocks unsupported offline mutation.
- Requires Owner review.
- Requires administrative review for high-risk conflicts.
- Opens a Security, Privacy, financial-integrity or operational Incident.
- Blocks the release.

Nexio must never:

- Treat a client cache as canonical financial truth.
- Upload one Owner's pending Intent under another Owner's Session.
- Use Device time as final shared ordering authority.
- Retry a mutation using a new operation identity.
- Silently overwrite a newer canonical Resource.
- Automatically merge conflicting financial amounts.
- Restore a deleted Resource through stale upload.
- Advance a cursor beyond uncommitted local changes.
- Present a rejected offline mutation as synchronized.
- Display a provisional balance as the verified canonical Current Balance.
- Discard valid pending financial Intents during replica repair without warning and governed recovery.

# Mobile and Web Synchronization Rule

Android and Web may use different storage engines, scheduling systems, lifecycle models and interface patterns.

They must nevertheless preserve one synchronization truth:

```text
The backend owns canonical state.

The client owns provisional local intent until backend acceptance.

Resource identity remains stable.

Resource versions remain explicit.

Owner scope remains mandatory.

Account scope remains validated.

Operation identity survives Retry.

Cursors advance only after committed local application.

Conflicts are detected before overwrite.

Tombstones prevent stale resurrection.

Financial values remain exact.

Pending state remains visible.

Rejected state remains visible.

Cross-Owner state never becomes visible or uploadable.
```

A local database is not correct merely because its transaction committed.

A Background Worker is not successful merely because it finished without an exception.

A Web tab is not authoritative merely because it became synchronization leader.

A Push signal is not a canonical change merely because the Device received it.

A locally calculated balance is not verified merely because all locally visible Transactions were summed.

When Android or Web cannot establish the current Owner, Resource version, cursor boundary, operation state, local integrity or canonical financial result, the client must prefer:

- Stopping mutation upload.
- preserving pending Intents.
- locking previous Owner state.
- marking replicas stale.
- requesting Authentication.
- performing a full authenticated refresh.
- surfacing conflicts.
- using a safe provisional financial presentation.
- rejecting unsupported schema.
- requiring an Application update.
- escalating cross-Owner anomalies.
- blocking unsafe release.

Nexio must never allow Platform differences to create different canonical meanings for the same Resource, mutation, conflict, deletion, financial value or synchronization state.
